# Agent Guidelines — ML Cookbook

This repo is a **learning environment owned by Adam, the author**. Agents assist; they do not take over. The default posture is: small, surgical changes that preserve the existing patterns, and no unsolicited feature expansion.

## Prime directive

**Do not implement ROADMAP.md items unless explicitly asked.** The roadmap is Adam's personal curriculum — building those features is the point of the project. If asked to "help" with one, prefer explaining, reviewing, or pairing over writing the whole thing.

When Adam *does* explicitly say to build something ("implement it", "go ahead"), that is the green light: build it end to end (core + tests + GUI + docs) rather than handing back pieces. Adam reviews the work afterward, so leave the repo green and the docs current. Logistic regression, decision trees, and random forests were built this way.

## Project shape

- `src/` layout, package `mlcookbook`, Python 3.12+, hatchling build.
- Install: `pip install -e ".[dev]"` · Test: `pytest` · Demo: `python examples/basic_usage.py` · App: `python -m mlcookbook`
- **Which Python:** this machine has 3.11, 3.12 and 3.13; bare `python` is 3.11 and does NOT have the project installed. Use `py -3.12 -m pytest` / `py -3.12 -m mlcookbook` (or activate a 3.12 venv). If you see "No module named mlcookbook/pytest", it's the wrong interpreter.
- Desktop app architecture: `gui/` is dumb presentation (signals out, data in; never imports the core), `src/mlcookbook` is the UI-free core, and repo-root `app.py` is the ONLY module that may import both. Keep it that way. Navigation is delete-and-redraw via `MainWindow.show_screen`; recipes route through `SCREEN_FACTORIES` in `app.py`. There is exactly one entry point (`python -m mlcookbook`); do not add others.
- Dependencies: pandas, numpy, scipy, scikit-learn, pyarrow; dev: pytest, ruff. The Neural Networks recipe uses scikit-learn's MLP. The optional `llm` extra (`torch>=2.6,<3`, `transformers>=4.57,<5`) was approved by Adam on 2026-10-19 for local LLM generation. Do not add other dependencies without asking. `.venv` contains the complete CPU LLM/dev/GUI/build runtime; `.venv/Scripts/python.exe` is the interpreter for this feature.
- Built so far: statistics (`correlation`, `chi_square`, `anova`, `association_scan`), regression (`linear_regression` with ridge/lasso and residual diagnostics, `decision_tree_regression`, `random_forest_regression`), classification (`logistic_regression`, `decision_tree`, `random_forest`, `svm`, `neural_network`, binary or multiclass; SVM and MLP also have regression twins), `kmeans`, and `pca`, all on a configurable, recorded preprocessing pipeline with training-only cross-validation. `visualization/` is intentionally skeletal (the app draws from result data); leave it that way unless told otherwise.
- The user launches the app from a Windows shortcut pointing at the PyInstaller build `dist/MLcookbook/MLcookbook.exe`, which is a **frozen snapshot**: source edits do not appear there until it is rebuilt (command in ADAM.md). After GUI or core changes the user will want to see, rebuild it and check the exe launches. `dist/` and `build/` are gitignored.

## Architecture rules (non-negotiable)

1. **Types drive applicability.** Columns get a `VarType` (`core/schema.py`) — a statistical role, not a pandas dtype. Analyses validate inputs against `Dataset.schema()` and raise or warn; never silently coerce.
2. **Results are data.** Every analysis returns a frozen dataclass mixing in `Result` (`core/results.py`) with a `warnings: list[str]` field. No analysis prints, plots, or logs. `result.to_dict()` must survive `json.dumps`.
3. **Warnings are part of the result.** Dropped rows, skipped columns, constant variables, assumption issues → `result.warnings`.
4. **No leakage.** Preprocessors come from `preprocessing.build_preprocessor()` unfitted and are fitted inside a sklearn `Pipeline` on training data only. Never fit anything on the full dataset before splitting.
5. **Libraries do the math.** Classical workflows use sklearn/scipy; LLM inference uses PyTorch/Transformers or external Ollama/llama.cpp runtimes. Orchestrate and validate; never reimplement numerical algorithms.
6. **Small public API.** Only add to `mlcookbook/__init__.py` deliberately. Everything else is imported from submodules.
7. **No enterprise patterns.** No factories, DI containers, deep inheritance, or clever metaprogramming. Type hints, dataclasses, composition, small modules.

## Desktop GUI conventions

- **Recipes are data + a factory.** A `Recipe` in `gui/recipes.py` (`variant="ready"`, a `key`), a thin screen class in `gui/screens/`, a demo entry in `DEMOS` and a builder in `REPORT_BUILDERS` in `app.py` (`SCREEN_FACTORIES` is derived from `DEMOS`). Ready screens (linear/logistic regression, decision tree, random forest, SVM, neural network, k-means, PCA, association scan) are ~10-line subclasses of `gui/screens/report_screen.py::ReportScreen` that declare their `task` (`"regression"`, `"classification"`, `"unsupervised"`) or `tasks` (tree/forest/SVM/neural network switch between classification and regression), and `params` specs (`int`/`float`/`choice` widgets whose keys app.py maps onto core arguments). `screen.request()` returns task, target, features, overrides, positive class (None = multiclass), params, preprocessing dict, and cv_folds.
- **Screens render a plain `report` dict** (documented at the top of `report_screen.py`): `dataset/target/features/settings` strings, optional `summary`, `tree`, `plots`, `metric_groups`, `bars`, `tables`, `warnings`. All numbers arrive pre-formatted as strings (or raw point lists for plots). **`app.py` does all result-to-report formatting**; `gui/` never imports `mlcookbook`.
- **Without an imported dataset, a ready recipe's first visit runs its built-in demo in a background job** (`DEMOS` in `app.py`: diabetes, breast cancer, wine; scikit-learn's bundled data) using the screen's default `request()`. Direct `SCREEN_FACTORIES[key]()` calls still build demo reports synchronously for tests and visual checks; the app uses `demo=False` and schedules the run. All screens support CSV/Parquet import with extra missing markers, a preview, persistent data checks, column-role overrides, target/feature selection, expandable model settings, and the Preprocessing & validation dialog. `app.py` owns imported data, background jobs, and per-recipe session snapshots. Screens expose plain `session_state()` / `restore_session()` data; navigation still deletes and redraws widgets. Snapshots preserve selections, all parameters, preprocessing, import controls, expanded sections, scroll positions, the last report, and the request that produced it. Returning restores without retraining, including unrun changes. A successful file replacement invalidates all snapshots; failed imports preserve them. Navigation snapshots are in memory; explicit Save/Open experiment persists one recipe and its dataset (see below). On a recipe's first imported-data visit, wait for Run Analysis. Thread completion and errors return to the GUI; the app waits for its active job when exiting.
- **Keep actions and state visible.** Run/status/progress live outside the form/report scrollers. A result banner distinguishes current settings from the last completed run; only successful runs replace the report's request. CSV options and model/validation controls start collapsed, the Python signature lives in About, and positive-class selection only appears for binary targets. Warnings have an always-accessible summary above the report. Long tables have bounded height and retain every row. Plain-language result summaries are formatted from core result data in `app.py`.
- **Report order:** after run metadata and the short summary, the recipe's main visual goes first (tree diagram, actual-vs-predicted scatter, fitted sigmoid, ROC curve, cluster projection, scree plot, strongest-pair detail), then plots, metric tiles (test, train, cross-validation mean ± SD), bars, tables (the preprocessing table last), warnings. Shared formatters live in `app.py` (`_cv_group`, `_preprocessing_table`, `_confusion_table`, ...). Metric captions are upper-cased by the stylesheet, so avoid Greek letters that look Latin in capitals (write RHO, ETA²).
- **Visuals are drawn with `QPainter`** (`gui/plot.py`: `PlotWidget`, `BarList`; `gui/tree_plot.py`: `TreeWidget`). Do not add matplotlib/plotly. Colors come from `gui/theme.py` (`ACCENT` violet, `PLOT_ALT` teal, `CATEGORICAL` palette addressed as `"c0"`..`"c9"` via `theme.palette`). To plot something, the **core result must carry the data** (e.g. `test_actual`/`test_predicted`, `test_probability`, tree `nodes`, k-means `projection`, PCA `scores`) — never recompute a model in `app.py`.
- **Verifying visually without a display:** construct `MLCookbookApp`, call `window.show_screen(SCREEN_FACTORIES[key]())`, `processEvents()`, then `window.grab().save("x.png")` and look at the PNG. Use the native Windows platform, not `QT_QPA_PLATFORM=offscreen` (offscreen has no fonts and renders tofu boxes). Flush `DeferredDelete` events between screens or the previous screen bleeds through.

## Templates to copy

- **Local LLM generation:** the eleventh recipe, `llm.generate_text` / `TextGenerationResult`, uses lazy optional imports and local unquantized safetensors checkpoints (`gpt2`, `llama`, `qwen2`, `qwen3`). No network access or custom model code. UI-free core returns text, exact formatted prompts, zero-based source positions, token counts/timing, stop reasons, model/ tokenizer/template fingerprint, device/precision, settings, versions, and warnings. Single prompts need no dataset; optional row generation requires exactly one string-valued text/categorical column, skips missing/blank rows, and caps rows/tokens/time. Token limits are explicit errors, never silent truncation. No sklearn preprocessing, training, or CV. `LLMScreen` uses `ReportScreen` with preprocessing/CV disabled, text/path/multiline params, and plain `text_sections` for copyable output. It sets `auto_run_demo=False`: opening a card shows setup and never loads/downloads weights. `app.py` wires cancellation through `_Job.requestInterruption` and a core callback checked between decoding steps; cancellation/failure preserves prior results. Save/Open restores text without loading weights; reruns need the external model folder. Runtime versions are read from metadata without importing torch for other recipes. `models/` is gitignored. Training/fine-tuning, quantized inference, embeddings, and graph execution remain separate until requested.
- **LLM checks and packaging:** `test_llm.py` and the LLM cases in `test_app_import.py` construct real tiny safetensors checkpoints offline. A separate CPU LLM CI job installs the optional extra. `build_windows.ps1` uses the isolated `.venv` runtime, explicitly collects the four supported model implementations and fast tokenizers plus runtime metadata, and excludes TensorFlow/vision/audio. Never restore the old `--exclude-module torch` build flag. Build, launch-check, and verify a real local model. The downloadable v1.0.0 release predates this recipe.
- **Ollama connector:** the same `llm` recipe card is now **Local LLMs**, with PyTorch/Ollama/llama.cpp engine controls. `mlcookbook.ollama` exposes `ollama_models`, `describe_ollama_model`, and `generate_ollama` from that submodule deliberately; root PyTorch exports remain unchanged. Standard-library HTTP connects only to loopback endpoints, checks installed models and rejects cloud references, never pulls weights or owns a server process. Frozen JSON-safe results record submitted prompts/messages, model digest/metadata, requested options, server version/usage, local wall time, and warnings. Server context truncation, applied device/precision, and exact rendered chat prompts are unverified. Private `_local_http.py` shares bounded HTTP and cancellation/deadlines even while idle; don't use blocking `socket.makefile` reads with timeout retries. Per-row deadlines include loading. `LLMScreen` emits connection signals and renders transient preview dictionaries; `_Job.progress` carries queued updates, and only successful runs replace completed reports. Save/Open works without a server or torch; `prepare_session` adds explicit defaults to legacy states before strict validation. `test_ollama.py` uses a fake HTTP server (fragmented UTF-8, chunked transport, errors, cancellation, deadlines, no optional imports); desktop cases cover streaming recovery, rows, offline reopen, and legacy migration.
- **llama.cpp connector:** `mlcookbook.llamacpp` deliberately exposes `llamacpp_models` / `generate_llamacpp` from that submodule, with frozen JSON-safe connection/generation results. Direct single-model loopback llama-server only: read `/health`, `/v1/models`, `/props`; chat-only `/v1/chat/completions` parses SSE independently of Ollama NDJSON, requires finish reason plus `[DONE]`, preserves usage-only terminal chunks, reasoning and explicitly returned applied settings. Missing usage/timings/version stay unavailable. Context/GPU offload/thinking are server startup settings, so hide Ollama and PyTorch-specific controls. No router, auth credentials, tools, model loading, server ownership, or downloads in product code. Optional `gguf_path` hashes only an explicitly selected local GGUF; never follow server-supplied filesystem paths, and never claim a file hash proves server-loaded identity or covers other shards/templates. UI `file` params use the file picker; `prepare_session` migrates both pre-Ollama and pre-llama.cpp states. `test_llamacpp.py` uses a fake fragmented/chunked SSE server; desktop tests cover loading, streaming cancellation, rows, offline restoration, and legacy Ollama state. Real CPU smoke model is `models/SmolLM2-135M-Instruct.Q4_K_M.gguf`, external to the bundle. Structured workflows are documented below; graphs and managed runtime setup remain separate milestones.
- **Saved experiments:** `mlcookbook.experiments` writes/reads versioned `.mlcb` ZIPs with JSON state/reports and a full typed Parquet dataset snapshot (SHA-256 verified). `MainWindow` emits Save/Open paths; `app.py` performs file work in `_Job`, validates a candidate screen before replacing the current session, and restores without training. Source paths/options are provenance only; reopening never rereads source files. Save one recipe explicitly, including unrun edits and last-report provenance. Failed saves/opens preserve current work. Do not use pickle or put fitted estimators in JSON results. Version differences belong in Data checks.
- **Model comparison:** `comparison.compare_regressors` / `RegressionComparisonResult` are exported deliberately. The tenth recipe compares ridge and forest regression with shared preprocessing, one split, and materialized training-only folds passed to `cross_validate_pipeline(..., splits=...)`. Select by mean CV RMSE, then fit/evaluate only that selected pipeline on the test holdout. Record exact zero-based source positions (independent of index labels), candidate settings, fold scores, selected-model metrics/predictions, and preprocessing. GUI parameters include seed/test fraction; comparison needs CV. Keep classification comparison and graph execution separate until requested.
- Coverage additions: `test_comparison.py` verifies shared folds, fitting boundaries, holdout-independent selection, serialization, and reproducibility; `test_experiments.py` verifies typed round-trips, fingerprint/version validation, and atomic-save recovery. `test_app_import.py` covers disk reopen for every recipe, missing original files, reruns, stale state, scroll, and failure recovery.

- New statistical test → follow `statistics/association.py` (validate types → compute with scipy → frozen result dataclass with warnings).
- New supervised workflow → follow `regression/linear.py` (validate via `regression/_problem.py` → `resolve_config` + `build_preprocessor(..., config=config)` in a `Pipeline` → train/test split → metrics via `evaluation/` → `training_cross_validation` on the training rows → `describe_preprocessor` → result dataclass with `preprocessing` and `cross_validation` fields).
- New classifier → follow `classification/logistic.py`; validation (target types, 2..50 classes, `positive_class` for two classes only, numeric targets with >10 values rejected as continuous, missing/imbalance warnings) is shared in `classification/_problem.py::prepare_classification_problem`, with `class_probabilities`/`metric_scores`/`task_for` helpers. Split is stratified. Metrics via `evaluation.classification_metrics` (binary labels ordered `[negative, positive]`; 3+ labels give macro averages and one-vs-rest AUC; ROC AUC is NaN, serialized as `null`, when undefined).
- Tree-style models: `resolve_config(preprocessing, scale=False)` so thresholds stay in real units (linear/logistic/k-means/PCA default to standard scaling, so linear coefficients are per-SD). `classification/tree.py` and `regression/tree.py` expose the fitted model as plain data (flat `nodes`, `rules`) with a CV-on-train-only depth curve. Forests carry encoded-feature importances and per-tree sizes; the classifier also carries held-out ROC coordinates (binary). Unsupervised workflows fit preprocessing on all rows (no held-out set exists).

## Testing

- **Structured text workflows:** `mlcookbook.llm_workflow` is a deliberately submodule-only API (`run_workflow`, frozen `LLMWorkflowResult`, `derive_dataset`, `compare_runs`, `export_workflow`). The same Local LLMs card has Extract/Summarize/Rewrite/Classify task presets, literal `{{column}}` bindings, nullable field roles and optional reference-column bindings. Server adapters accept optional `response_schema` without changing free-generation behavior. Independently validate exact flat JSON fields/types/labels; no repair, silent coercion, extra/duplicate fields, NaN or infinity. Record per-row outcomes/raw output/provenance. Batches count 1–10 source positions, including skips; cancellation retains completed rows and marks unfinished rows. Unlike free generation, row-level errors produce a completed outcome report. Retries create new artifacts only for matching source/configuration and observed model/runtime identity; ignore llama.cpp's transient model-list `created`/status fields, retaining their full raw metadata per row. File-to-loaded-model binding remains unverified. Dataset fingerprints include Parquet values/order/index/dtypes and statistical roles; derive with nullable arrays assigned by position, preserving duplicate index labels and every source column. Reference labels cannot be prompt bindings; exact agreement uses valid non-null pairs with coverage, while validation rate includes all selected positions. Keep ten recent runs in report JSON, compare selected compatible runs, export JSON explicitly. Saved experiments restore without servers, with exact legacy parameter-default migrations. `app.py` performs joins, metrics/report formatting, jobs and explicit derived-dataset acceptance; `gui/` only emits actions/renders plain data. Returning to Local LLMs retains the source run while other recipes receive the derived snapshot. Tests: `test_llm_workflow.py` plus desktop disk/retry/export/compare/lineage cases. Graph execution/editor and GGUF/model architecture inspection remain separate milestones.

- Every behavior change needs pytest coverage; shared fixtures live in `tests/conftest.py` (`mixed_df`, `linear_df`, `logistic_df`).
- Every new result type needs a `json.dumps(result.to_dict())` round-trip test.
- Coverage map: `test_io.py` (formats, leading zeros, markers, dates), `test_pipeline.py` (config, summaries, quality, CV, leakage per fold), `test_multiclass.py`, `test_regression_models.py` (ridge/lasso, diagnostics, tree/forest regression), `test_unsupervised.py` (k-means, PCA), `test_svm_nn.py` (SVM and MLP, both tasks), `test_statistics.py`, `test_app_import.py` (desktop import/run/recovery/navigation, every recipe's demo, tasks, params, preprocessing; requires PySide6), `test_preprocessing.py` (nullable training-only imputation).
- Forest coverage: `tests/test_forest.py` checks leakage (including inside every CV fold), ROC/probability/class ordering, serialization, reproducibility, warnings, and input validation.
- Run `pytest` and `ruff check .` before declaring anything done; CI (`.github/workflows/ci.yml`) runs both, the app tests on Windows with `QT_QPA_PLATFORM=offscreen`.

## Definition of done for a new recipe

1. Core function + frozen result + `json.dumps` test (reuse shared helpers). 2. Exported deliberately from `mlcookbook/__init__.py`. 3. `pytest` green. 4. GUI recipe flipped to Ready with a screen and factory; render it and look at it. 5. README/AGENTS/ADAM updated. 6. Rebuild the exe if the user launches from the shortcut. 7. Don't commit unless asked.

## Windows gotcha

This machine is Windows. **Files must be UTF-8** — the original README was UTF-16 and broke the hatchling build. If a build fails with `UnicodeDecodeError`, check file encodings first.
